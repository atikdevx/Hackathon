==================================================
PRIMARY OBJECTIVE
==================================================

Build ONE production-ready HTTP service that:

1. Accepts a 24-hour smart-campus energy scenario.
2. Accepts 1–3 natural-language operator notes.
3. Uses a real language-capable generative model to interpret every operator note.
4. Converts each note to exactly one supported structured directive or no_op.
5. Passes the LLM output through deterministic guardrails.
6. Applies all valid directives to the optimization model.
7. Computes a valid 24-hour electricity schedule.
8. Minimizes total grid electricity cost.
9. Returns the exact required JSON response.
10. Is robust, deployable, testable, Dockerized, and reproducible.

End-to-end architecture:

HTTP Request
→ Request Validation
→ LLM Interpreter
→ Deterministic Guardrail Validator
→ Directive Application
→ Energy Optimizer
→ Final Schedule Replay Validator
→ Totals/Recalculation
→ JSON Response

==================================================
2. LLM INTERPRETER
==================================================

The LLM is MANDATORY.

A language-capable generative model MUST directly interpret operator_notes and produce structured directive_interpretation that is actually used by the optimizer.

Using AI only for:
- plan_summary
- documentation
- comments
- cosmetic text

does NOT satisfy the challenge.

Do not use hard-coded phrase matching as the sole interpreter.

Hidden cases will paraphrase directives.

For EACH operator note, return EXACTLY ONE interpretation entry in note_index order.

Supported directive types are exactly:

1. solar_reduction
2. minimum_battery_reserve
3. no_charge_window
4. no_discharge_window
5. max_grid_window
6. no_op

No other directive type is allowed.

Required structured forms:

solar_reduction:
{
  "hours": [...],
  "factor": number
}

minimum_battery_reserve:
{
  "hours": [...],
  "minimum_energy_kwh": number
}

no_charge_window:
{
  "hours": [...]
}

no_discharge_window:
{
  "hours": [...]
}

max_grid_window:
{
  "hours": [...],
  "max_grid_kwh": number
}

no_op:
null

Interpretation output format:

{
  "note_index": integer,
  "applies": boolean,
  "directive_type": string,
  "structured_adjustment": object | null,
  "explanation": string
}

Semantics:

For no_op:
- applies = false
- directive_type = "no_op"
- structured_adjustment = null

For every other directive:
- applies = true
- exact required structured_adjustment shape

The LLM must:
- distinguish relevant vs irrelevant notes
- understand paraphrases
- understand percentages
- understand equivalent numeric wording
- understand 12-hour and 24-hour time expressions
- handle “from X to Y” using start-inclusive, end-exclusive intervals

Example:
1 PM to 3 PM → [13, 14]

solar_reduction.factor means usable fraction REMAINING.

Example:
“80% reduction” → factor = 0.2

The LLM must NEVER invent:
- demand
- tariff
- solar baseline
- battery values
- unsupported directive types

Prefer structured-output / JSON-schema-capable LLM invocation if supported by the chosen provider.

Make model/provider configurable via environment variables.

Do not hardcode API credentials.

If reasonable, design the provider integration so the model implementation can be swapped with minimal code changes.

4. DIRECTIVE APPLICATION
==================================================

Apply all validated directives BEFORE optimization.

Deterministic behavior:

solar_reduction:
effective_solar[h] = original_solar[h] * factor

minimum_battery_reserve:
battery_energy_after_kwh[h] >=
max(
  base minimum_energy_kwh,
  directive minimum_energy_kwh
)

no_charge_window:
battery charging = 0 for listed hours

no_discharge_window:
battery discharging = 0 for listed hours

max_grid_window:
grid_kwh[h] <= max_grid_kwh

no_op:
no model change

Multiple valid directives may exist in one scenario.

Implement them cleanly and compositionally.

5. ENERGY OPTIMIZER
==================================================

Implement a correct mathematical optimizer.

Use a practical exact optimization method such as:
- Linear Programming
- another mathematically correct solver

Choose a solver/library suitable for:
- fast execution
- deterministic behavior
- easy Docker installation
- reproducibility

Do not use an LLM to calculate the energy schedule.

Optimization objective:

minimize

SUM over h=0..23:
grid_kwh[h] * tariff_bdt_per_kwh[h]

Correctness is more important than cost.

A cheaper schedule that violates a constraint is INVALID.

==================================================
ENERGY RULES
==================================================

For every hour, maintain valid energy accounting.

Battery state:

If charge:
E_after = E_before + battery_kwh

If discharge:
E_after = E_before - battery_kwh

If idle:
E_after = E_before
battery_kwh = 0

Battery bounds:

minimum_energy_kwh <= E_after <= capacity_kwh

If a minimum_battery_reserve directive applies, use the higher active minimum.

Charge limit:

battery_kwh <= max_charge_kwh_per_hour

Discharge limit:

battery_kwh <= max_discharge_kwh_per_hour

Solar:

0 <= solar_used_kwh <= effective_solar_kwh

Unused solar may be curtailed.

Grid export is NOT part of this challenge.

Energy balance must hold every hour:

grid_kwh
+ solar_used_kwh
+ battery_discharge_kwh

=

demand_kwh
+ battery_charge_kwh

Grid must be non-negative.

All required numeric outputs must be finite and non-negative.

End-of-day battery neutrality:

battery_energy_after_kwh at hour 23
==
initial_energy_kwh

within accepted floating-point tolerance.
